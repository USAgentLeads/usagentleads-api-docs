---
title: "Plans and credits"
---
| Operation | Record credits |
| --- | --- |
| Search or lookup returning a new agent | 1 per record |
| Search or lookup returning a new brokerage | 2 per record |
| Repeat access to records acquired through dashboard, REST or MCP | 0 |
| Count, preview, coverage, locations, account, usage and request recovery | 0 |
| Export creation, polling, cancellation and repeat download | 0 |
| Export preparation | Only newly acquired records |
| Missing, suppressed or contactless records | 0 |

Growth includes 10,000 successful/in-flight API requests per UTC month; Pro includes 100,000. Both include REST v3 and MCP. Monthly request quotas, record credits and per-minute limits are separate. Failed HTTP requests do not count toward the successful-request quota; MCP protocol requests and successful tool-response envelopes do.

A synchronous request is all-or-nothing: exceeding `max_credits` returns 409; insufficient balance returns 402. Neither acquires part of the selection. Set `max_credits: 0` when you only permit already-owned data.

An export freezes its selection at creation and charges at preparation. It does not reserve credits while queued. If the balance is insufficient then, the job fails without acquiring records. Cancel before preparation to avoid spending.

A response's `credits.charged` records the original transaction. A replay returns that historical receipt and never charges it again. Results remain recoverable for 30 days; expired keys remain tombstoned and cannot be reused.
